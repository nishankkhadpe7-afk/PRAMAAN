## Iteration 2026-10-10 — differentiated detectors completed + MCP egress security layer
- **T11 physical plausibility (P1–P5):** fully implemented in `backend/p3.py`. P1 route/time feasibility (implied road speed vs a versioned hard maximum), P2 vehicle overlap (one vehicle on overlapping movement windows), P3 load estimate (quantity vs capacity), P4 event order (arrival before departure), P5 PIN/consignee (consignee GST state vs billed buyer state). `IMPOSSIBLE` is emitted ONLY for a hard speed violation on a configured verified-channel timestamp (`verified_gps_telematics`); every other conflict is `INCONSISTENT`/`REVIEW` because synthetic route facts are unverified. All T11 parameters live in `p3_ruleset.yaml` `t11` and are labelled `synthetic_test_only`.
- **T02 graph cycles:** real elementary directed-cycle detection over the counterparty graph (`detect_cycles`), replacing the old union-find heuristic. Cycles are REVIEW patterns, never automatic fraud; the detected cycle in the fixture is `CUST-002 → CUST-004 → CUST-006 → CUST-002`. Convergence (two parties sharing one director) is correctly NOT reported as a cycle.
- **T13 official-style cryptographic verification:** new `backend/p3_crypto.py` performs real Ed25519 signature verification of a signed e-invoice QR envelope against a *configured trusted key*, cross-checks the signed payload fields against the books, and flags registration-timing (backdating) risk. Ships with a clearly labelled DEMO key (`DEMO_IRP_TEST_ONLY`) that can only yield `GOVERNMENT_REGISTERED_DEMO` and never sets `externally_verified`/`government_registered`; dropping a real NIC/IRP public key + `key_classification=OFFICIAL_IRP` into the `t13` ruleset block upgrades it with no code change. A later acknowledgement is a risk indicator only; T13 never emits `IMPOSSIBLE`.
- **MCP egress data-loss-prevention layer (`backend/mcp_dlp.py`):** at the MCP boundary, before any tool result reaches the external AI agent, sensitive identifiers (GSTIN, PAN, bank/financial account, phone, email) are redacted by default and a configured high-sensitivity category (financial account numbers) is hard-denied; structural ids and hashes are preserved. Every redaction/denial is logged to the hash-chained audit trail via `POST /p4/egress-audit` (`mcp_egress_filtered` events), giving an auditable record of exactly what the AI was prevented from seeing. This narrows egress on top of — not instead of — the existing server-side authorization and role boundaries.
- **Fixtures + manifest re-frozen:** `data/movement_routes.csv`, `related_party_edges.csv` and `invoice_verification_status.csv` were extended with the fields these detectors need (timestamps, PINs, vehicle, consignee GSTIN, signed QR envelope, IRN ack date); all `data/*.csv` were normalized to canonical LF (fixing a prior CRLF/manifest drift) and `source_manifest.json` was regenerated (`dataset_version` 1.1, 60 data rows, 13 files). NOTE: historical/frozen export hashes and dataset IDs from earlier runs change as a result and must be re-frozen; no production verification is claimed.
- **Tests:** backend suite now 44 passing (35 prior + 9 new in `tests/test_security_layer.py`), including the external MCP SDK console over stdio and Streamable HTTP exercising the DLP layer. Updated expectations in `tests/test_p3.py` and `tests/test_p5.py`.
- **Still honest about limits:** the signed-QR path is DEMO crypto, not NIC/IRP; route/verification facts are synthetic and unverified; SQLite still has no real DB roles; no external anchoring; hosted-client interoperability remains to be tested on the judge's actual clients.
